# Fixes log

**Date:** 2026-11-04

A short record of problems found and how they were fixed, so you can compare the fix with other ways to solve the same problem. Newest first. Feature work goes in [the build notes](06_2026-11-04_build-notes.md); this file is only for problems.

Each entry says:
- **Problem:** what was wrong, as you saw it
- **Fix:** what changed, and whether it was code, art or data
- **Other ways:** how other developers often solve it, and why we didn't (or might later)

---

## 2026-11-09: The big button flickered while carrying a building (playtest finding 102)

- **Problem:** moving a lifted building around, the big button kept changing picture.
- **Fix (code):** the tile ahead switches between free and taken as you walk. On a taken one the button showed its "nothing to do" picture, the Move icon, so it swapped back and forth. Now Build mode's "nothing to do" picture is the building being carried or placed, only dimmed.
- **Other ways:** wait a moment before changing the picture (debounce), or never dim at all. Keeping one picture is simplest, and the dimming still says "not here".

## 2026-11-08: The big button kept the attack picture after leaving Combat mode (playtest finding 100)

- **Problem:** in Farm or Build mode with nothing to do, the big button still showed the attack slashes, dimmed.
- **Fix (code):** with nothing to do, the button kept whatever picture it last had. Now it shows its mode's own picture, dimmed: the hoe in Farm mode, the build tool in Build mode, the slashes in Combat mode (`TouchControls._idle_icon()`).
- **Other ways:** hide the picture when there's nothing to do, or swap the whole button per mode. A dimmed picture of the mode keeps the button easy to find.

## 2026-11-08: The combat tab pushed its popup off the screen (playtest finding 95)

- **Problem:** on the Modes page's Combat tab, picking the sword listed six big buttons (remove and sooner for each of three combat buttons), so the popup grew taller than the screen and looked broken.
- **Fix (code):** the tab shows one row per combat button, with every carried weapon; a tap turns it on or off for that button. The details side keeps at most two buttons, and it now scrolls, so no item can push a menu off the screen.
- **Other ways:** a popup per combat button, or drag and drop into slots. Rows of tap switches match the farm jobs, so there's one way to learn.

## 2026-11-08: A mode wheel test failed now and then (found while building findings 90 to 93)

- **Problem:** "letting go off the wheel changes nothing" failed: the release counted as a tap and changed the mode.
- **Fix (test only):** the test held the mode button for 30 frames, but headless frames can be very short, so the 0.3 second hold sometimes never finished. It now waits real time (`create_timer`).
- **Other ways:** run timing tests with `--fixed-fps 60`, or fake the held time. Waiting real time is closest to a finger.

## 2026-11-08: A test overwrote the PC save (a mistake by Claude)

- **Problem:** while checking one test, Claude ran it without a temporary home folder, so its `end_day()` wrote a test game over the user's PC save.
- **Fix (process):** single tests always get a temporary `APPDATA`, as CLAUDE.md says; `tests/run_all.sh` already does this. The phone's save wasn't touched.
- **Other ways:** have the game pick a test save folder by itself when run with a `--test` flag, so a forgotten setting can't reach the real save. Worth doing if it happens again.

## 2026-11-08: A picked-up shipping box seemed lost (playtest finding 76)

- **Problem:** in Build mode the user picked up the shipping box to move it, and it vanished. The bag was full, so it went to the storage chest, and the only sign was a short notice.
- **Fix (code):** Build mode won't pick a building up when the bag has no room for it; it says "Your bag is full. Put something in storage first." The guard square also stops showing when there's nothing to place (`Farm._nothing_to_build()`).
- **Other ways:** let the pick-up go straight to storage with a clear arrow to the chest, or let buildings skip the bag limit. Refusing is simplest, and nothing can end up somewhere the player didn't choose.

## 2026-11-08: The bag's order changed after loading (found while building the storage prototype)

- **Problem:** the order of items in the new bag came back alphabetical after a save and load, so items would jump around on the bag page overnight.
- **Fix (code):** a saved dictionary comes back with its keys sorted, so the bag is saved as an ordered list of [item, count] pairs instead (`Inventory.save_to()`). A test copies the save through text, like a real file, to catch it.
- **Other ways:** save a separate list of the order, or give each slot a number. A list of pairs keeps one value with no way for the two to disagree.

## 2026-11-07: A ripe wardthorn guarded nothing on phones (playtest finding 60)

**Problem:** the land around a ripe wardthorn was taken by the curse, even though it was still planted.

**Fix (code and data):** it only guarded while watered, but on a ripe plant the big button only bursts, so a phone could never water it. Now a ripe one needs no water and guards 5×5, and a dry growing one guards 3×3, so a planted wardthorn always does something. The sizes are `ward_dry_radius` and `ward_ripe_radius` on `CropData`.
- Files: `scripts/farm/farm.gd`, `scripts/farm/crop_data.gd`, `data/crops/wardthorn.tres`, `tests/test_guards.gd`

**Other ways:** let the big button water a dry ripe plant first (then one tap waters and the next bursts, which is easy to mistake), or add a second button for bursting (more buttons, which we removed)

## 2026-11-07: Action opened the workbench instead of farming (playtest finding 49)

**Problem:** farming near the workbench, house or shop kept opening them, even with your back to them.

**Fix (code):** the big button only uses an object inside a small circle in front of the player. F still uses anything in reach. The plan's chart put objects first, and that was right only for objects you're facing.
- Files: `scripts/player/player.gd`, `scripts/farm/farm.gd`, `tests/test_smart_action.gd`

**Other ways:** make the tile win over objects (then you couldn't reach the box past a crop), shrink the reach (makes objects hard to use), or keep a separate button (what we removed)

## 2026-11-07: The book's parchment art was partly see-through

**Problem:** the art looked solid, but about half of it was see-through, including a ring around the middle. On a bright test background, the world showed through where the text would sit.

**Fix (art and a tool):** `tools/build_book_page.gd` flood fills from the border through see-through pixels, so only the true outside is cleared, and everything inside the torn edge becomes solid. Cutting by transparency alone made the ring worse.
- Files: `tools/build_book_page.gd`, `assets/ui/book_page.png`, `data/ui/book_panel.tres`

**Other ways:** ask the AI for a new image (slow, and it may do the same again), paint it by hand in an image editor (best for final art), or draw a solid color behind the page in the menu (quick, but the torn edge would be lost)

## 2026-11-07: `GameState` had grown too big (playtest finding 26)

**Problem:** one 476-line file held money, crafting, the day, health and saving, so every change touched something unrelated. The next controls steps would have made it worse.

**Fix (code):** it's now four autoloads: `Inventory`, `Progress`, `SaveGame`, and a small `GameState` for what the whole game shares. The game plays the same and the save file has the same keys in the same order, so old saves still load. Each part now saves and resets its own values. Tests changed only their paths, and `tests/test_save_parts.gd` is new.
- Files: `scripts/autoload/`, `project.godot`, every script and test that used the moved names

**Other ways:** keep one file and only group it with comments (no real gain), make each part a plain class held by `GameState` (one global name, but longer calls everywhere), or use signals only between parts (looser, but much harder to follow for this size of game)

## 2026-11-07: The joystick reached the hearts and left the screen (playtest finding 35)

**Problem:** the ring came up close to the hearts, and near the corner it was partly off the screen.

**Fix (code):** Godot's built-in `VirtualJoystick` has no way to limit its ring, so `ThumbStick` replaces it. A thumb wakes it only in the lower left area. The ring stays inside a safe area, so the whole stick shows. The push is measured from where the thumb landed, so a touch at the edge doesn't make the player walk. It also dims when not touched.
- Files: `scripts/ui/thumb_stick.gd`, `scripts/ui/touch_controls.gd`, `scenes/main/main.tscn`, `tests/test_touch.gd`, `tests/test_wide_screen.gd`

**Other ways:** a fixed joystick (simplest, but thumbs drift off it), hiding the ring until touched (cleaner, but new players can't see it), or a store-bought joystick plugin (more settings, but one more thing to keep working with each Godot version)

## 2026-11-07: The curse warning ran off the screen (playtest finding 34)

**Problem:** facing a marked tile on the computer, the end of the message was cut off at the right edge.

**Fix (code):** the text is shorter, and a test measures it against the screen. Computers show these messages on one line, so long text doesn't wrap.
- Files: `scripts/farm/farm.gd`, `tests/test_curse_returns.gd`

**Other ways:** turn on wrapping for computers too (safest for translations later), or shrink the text to fit, which makes it harder to read

## 2026-11-07: Messages sat on top of the tool bar (playtest finding 27)

**Problem:** on the computer, a message like "The curse has marked 3 tiles for tonight." touched the tool icons and their numbers.

**Fix (code):** the message positions were set before the tool bar existed, so they moved up 8 pixels on computers and phones. Tests now check the gap on both.
- Files: `scripts/ui/touch_controls.gd`, `tests/test_wide_screen.gd`

**Other ways:** a dark strip behind the text (easier to read over busy ground, and still possible), or a message area that measures the tool bar in code, which is safer if the bar changes size

## 2026-11-07: The thumb went past where the joystick works (playtest finding 22)

**Problem:** on the Redmi Turbo 4 Pro, the thumb kept going past the area where the joystick could be moved.

**Fix (code and a scene setting):** the touch area stayed 190×180 on every phone, which is small on a wide screen. It now covers the left side, from below the hearts down to the bottom and across to the tool bar: 332×366 on this phone. The joystick also went from Dynamic to Following, so the ring follows a thumb that slides past it, and a short move back turns the player at once. The bigger area reached under menus, so the joystick now sleeps while a menu is open and releases any movement.
- Files: `scripts/ui/touch_controls.gd`, `scenes/main/main.tscn`, `tests/test_touch.gd`, `tests/test_wide_screen.gd`

**Other ways:** a bigger ring (more thumb travel, but it hides more of the game, so it's the next thing to try if needed), the whole left half of the screen (the same idea, but it would run under the tool bar), or a setting for joystick size, which many mobile games add later

## 2026-11-05: Message text ran under the phone buttons (playtest finding 20)

**Problem:** with the phone controls on, a long message at the bottom went under the joystick and the `<` button, hiding some words.

**Fix (code):** on phones the messages now stay in the space between the joystick and the seed arrows, wrap onto a second line when needed, and grow upward. Notices sit above the crop and object text. Computers keep one line in the old place (`TouchControls._fit_messages()`).
- Files: `scripts/ui/touch_controls.gd`, `tests/test_wide_screen.gd`

**Other ways:** shorter messages (helps, but one long item name brings it back), a smaller font (harder to read on a phone), or a dark strip behind the text, which could still be added if text is hard to read over the ground.

## 2026-11-05: Too much space above the hearts on phones (playtest finding 19)

**Problem:** on phones there was an empty gap above the hearts.

**Fix (code):** the gap was the computer's keyboard help line, which is hidden on phones. With touch controls on, the hearts and tool text now move up 24 pixels into its place (`TouchControls._use_hint_room()`). Computers keep the help line.
- Files: `scripts/ui/touch_controls.gd`, `tests/test_wide_screen.gd`

**Other ways:** a container (like a flex column in CSS) that closes the gap by itself when the hint hides. It's the tidier choice if the HUD grows, but it would mean rebuilding the top left of the HUD for two items.

## 2026-11-05: The pause button looked odd in the middle of the screen (playtest finding 18)

**Problem:** on phones the pause button sat alone at the top center, over the game world.

**Fix (code):** it moved to the top right corner. Day, money and the status text move 40 pixels left while the phone controls are on (`TouchControls._make_room_for_pause()`). We tried it beside the hearts first, but it looked like part of the health bar. It still looked weird in the corner, because the real problem was the icon: the dark bars filled the circle and sank into the curse. The icon is now about half size and bone-white, set in code with no new art.
- Files: `scripts/ui/touch_controls.gd`, `tests/test_pause.gd`, `tests/test_wide_screen.gd`

**Other ways:** putting pause inside the Bag menu for a cleaner screen, but it would be harder to find and slow to reach during a fight.

## 2026-11-05: Menus weren't in the middle of the screen on phones (playtest finding 17)

**Problem:** with the phone controls on, the pause menu and other menus sat left of center.

**Fix (code):** every menu used to sit at 39% across on touch screens, to stay clear of the Act button that closes it. Now each menu is centered, and `GameMenu._place()` shifts it left only as far as needed, so only a very wide menu (a full bag or the workbench on a 16:9 screen) moves. It runs again when a menu changes size.
- Files: `scripts/ui/game_menu.gd`, `scripts/ui/touch_controls.gd`, `tests/test_phone_ui.gd`, `tests/test_wide_screen.gd`

**Other ways:** hiding the side buttons while a menu is open and giving every menu its own close (X) button, which is common on phones. It would need a new button on each menu, so we kept Act.

## 2026-11-05: Hard to walk left with the joystick on a phone (playtest finding 15)

**Problem:** the joystick sat in a fixed spot too close to the screen edge, so there was little room to push left, and the thumb kept missing its center.

**Fix (setting and code):** the joystick now uses Godot's Dynamic mode: it starts wherever the thumb lands inside a 190×180 area at the bottom left, and its resting spot moved 30 pixels inward. On wide screens Use, Act, Bag and the seed arrows also move up to 20 pixels in from the right edge.
- Files: `scenes/main/main.tscn`, `scripts/ui/touch_controls.gd`, `tests/test_touch.gd`, `tests/test_wide_screen.gd`

**Other ways:** a fixed stick moved inward (simple, but the thumb still has to find it), Following mode where the ring also trails the thumb (one setting away if Dynamic isn't enough), or a settings option so players choose, which many mobile games offer.

## 2026-11-05: Black bars on all sides on a real phone (playtest finding 14)

**Problem:** on the phone the game sat in a small box, with black bars on every side.

**Fix (code and setting):** the game kept a 16:9 picture at a whole-number scale, so a 2772×1280 screen got 3× (1920×1080) and the rest was black. The new `ScreenFit` autoload picks the biggest whole-number scale, then sizes the view to match the screen (924×426 there). Pixels stay sharp and the buttons stay the same size, and the player sees more of the island. The HUD labels now use anchors, and touch buttons and the computer tool bar follow their screen edge.
- Files: `scripts/autoload/screen_fit.gd`, `project.godot`, `scenes/main/main.tscn`, `scripts/ui/touch_controls.gd`, `scripts/ui/key_tool_bar.gd`, `tests/test_wide_screen.gd`

**Other ways:** Godot's `expand` aspect with `fractional` scale is the common one-line fix, but pixels come out uneven at 3.55×. `expand` with `integer` looks right but still leaves bars (we tried it, and a test caught it). Keeping the bars and filling them with border art is also common in pixel games, but wastes a phone's small screen.

## 2026-11-05: Crop needs were only text at the bottom (playtest finding 13)

**Problem:** what a crop needed only showed as text, and only for the tile you faced.

**Fix (code and art):** a water drop floats over crops that need water and a sparkle over ripe ones, gently bobbing; crops with nothing to do show nothing, so a big field stays calm. The "Empty soil" text now only shows on its last night.
- Files: `scripts/farm/crop.gd`, `scripts/farm/farm.gd`, `assets/ui/need_water.png`, `need_ripe.png`, `tests/test_crop_needs.gd`

**Other ways:** an icon on every tile all the time (noisy), or relying on the crop and soil look alone, as some PC farming games do.

## 2026-11-05: Nothing to buy for the first 4 days (playtest finding 12)

**Problem:** found by the math check, not by playing. You start with no money, and the first crop pays out on the night of day 4, so healing, the game's main reward, couldn't start until day 5.

**Fix (data):** new games start with 2 free holy water, set by `start_holy_water` in `data/balance.tres`. Existing saves keep what they have.
- Files: `data/balance.tres`, `scripts/farm/game_balance.gd`, `scripts/autoload/game_state.gd`

**Other ways:** starting money (more freedom, but it may go on seeds), a first quest that hands out holy water, a faster first crop, or a scripted first cleanse as a tutorial. Many games give the core reward right at the start for this reason: the first minutes show players what the game is about.

## 2026-11-05: Aiming at rocks, trees and soil took many nudges (playtest finding 11)

**Problem:** reaching a rock or tree took several small steps and turns before the cursor landed on it. Not a bug, but it didn't feel smooth. Three causes: the target was only the one tile right ahead of the feet, so standing half a row off missed; walking diagonally makes you face sideways; and objects look bigger than the one tile that counts.

**Fix (code):** smart targeting (aim assist). The tile ahead still comes first. If the current tool can't use it, the two tiles beside it are tried, the side nearer the player first, and the cursor moves to the one that works, so you always see what will happen. The Hoe and Build tools stay exact, because they create something where you aim, and a guess could till or build on the wrong tile.
- Files: `scripts/farm/farm.gd` (`smart_target_for()`, `EXACT_TOOLS`), `tests/test_targeting.gd`

**Then sticky facing (code):** walking diagonally always turned you sideways. Now you keep your facing while it's within 60° of where you're walking, so walking down-left while facing down stays down. No new art.
- Files: `scripts/player/player.gd` (`_facing_for()`, `STICKY_FACING`)

**Other ways:** aim with the mouse (PC Stardew), which doesn't help phones; a bigger reach that picks the nearest usable object in a circle around the player (stronger assist, but it can pick something behind you); or diagonal facing poses, which need art for 4 more directions, idle and walking. Some games also let a direction tap turn you without stepping.

## 2026-11-04: The target highlight was a plain square (playtest finding 10)

**Problem:** the box showing which tile your tool will act on was a thin white or red rectangle drawn in code, the one thing on screen that didn't look like the rest of the art.

**Fix (art and code):** a cursor image of four bone-white corners. The art was ordered with three rules so one image covers every case: light colors (the code tints it red where the tool can't be used), corners only with nothing between (drawn as a 9-slice, so it stretches to holy water's 3×3 or 5×5 patch with sharp corners), and thin. It sits 4 pixels outside the tile so it frames the soil instead of covering it, and it pulses gently.
- Files: `assets/ui/tile_cursor.png`, `scripts/farm/tile_highlight.gd`, `tests/test_cursor.gd`

**Other ways:** corner brackets drawn in code (no art, Claude's first suggestion), a soft glowing tile, or a bouncing arrow above the target. Some games hide the cursor where the tool can't be used, but red tells the player why nothing happens.

## 2026-11-04: Watered soil had hard straight edges (playtest finding 8)

**Problem:** watered soil is a separate, darker tile, so where it met dry soil the border was a straight line along the grid.

**Fix (code, plus an image made by a script):** a new `WetEdges` node draws a thin ragged edge of wet soil over the dry soil beside it, the same trick as the grass and curse edges. The edge tool now takes a depth per atlas, and the wet one is half as deep (about 1 to 6 pixels instead of 2 to 12), so each watered tile is still easy to tell apart.
- Files: `scripts/farm/wet_edges.gd`, `assets/tiles/wet_edge.png`, `tools/build_curse_edges.gd`, `scripts/farm/farm.gd`

**Other ways:** many farming games keep watered tiles as hard squares on purpose, because the edge shows exactly which tile still needs water. Others draw a wet "splotch" inside each tile instead of changing the whole tile. A light edge is a middle way: softer, but still readable.

## 2026-11-04: The tool was only text on computers (playtest finding 9)

**Problem:** phones had a tool bar with icons, but computers only showed "Tool: Watering can" at the bottom.

**Fix (code, no new art):** a `KeyToolBar` shows the same icons in the same place, with each tool's number key; the selected one is highlighted, and clicking a slot picks that tool. The tool text moved up under the hearts, where it already sat on phones, which also removed a small bug: switching touch controls on and then off used to leave the text at the top.
- Files: `scripts/ui/key_tool_bar.gd`, `scripts/ui/touch_controls.gd`, `scenes/main/main.tscn`

**Other ways:** most PC farming games use exactly this, a hotbar along the bottom. Some only show a single icon of the current tool next to its name, which is less work but less helpful.

## 2026-11-04: Fences in a vertical line looked broken

**Problem:** fences only had side-on art, so a line placed up and down looked like a stack of separate side-on pieces, with rails sticking out sideways.

**Fix (art and code):** a new vertical fence image, and each fence now checks its neighbors: fences above or below, but none beside, mean vertical art and a tall collision shape (so the line has no gaps). The builder asks every fence to check again after placing, picking up and loading.
- Files: `assets/objects/fence_vertical.png`, `scripts/farm/fence.gd`, `scripts/farm/builder.gd`

**Other ways:** the full version is a set of 16 pieces (every mix of neighbors: ends, corners, T-joins, crosses), like Godot's terrain autotiling for tiles. It looks best but needs much more art. We have 2 of the 16 so far; ends and corners are open item 5 in [the playtest findings](19_2026-11-04_playtest.md).

## 2026-11-04: A lantern test failed about 1 run in 500

**Problem:** `test_growth` checks that two lanterns don't flicker together. It failed once in many runs. The flicker is two waves with a 2.3 speed ratio, so it repeats exactly every ~10.5 seconds; when two lanterns' random start times happened to be a whole repeat apart, they flickered identically. Players wouldn't notice, but the test did.

**Fix (test):** the test now sets the two lanterns' start times 1 second apart instead of trusting luck.
- Files: `tests/test_growth.gd`

**Other ways:** add a third wave with an odd speed so the pattern never repeats exactly, or seed each lantern by its position. Worth it only if lanterns ever visibly flicker in sync.

## 2026-11-04: An out-of-date weak spot: "player still uses grounded movement"

**Problem:** the build notes listed this as a weak spot for step 6, but `player.tscn` already has `motion_mode = 1` (Floating).

**Fix (docs):** removed from the "Things to do better" table. **Lesson:** check the code before fixing something a doc says is broken.

## 2026-11-04: "Leaked instances" when quitting during a sound

**Problem:** once real sound files existed, almost every test failed with "ObjectDB instances were leaked at exit". A test quits right after an action, while its sound is still playing, and Godot can't finish cleaning up a sound that's mid-play when the program ends.

**Fix (code):** with no window (`DisplayServer` is "headless", as in the tests), `Audio` picks the sound but doesn't start it. Nothing can be heard there anyway, and tests still check which sound was asked for.
- Files: `scripts/autoload/audio.gd`

**Still there:** the real game shows the same warning in the console if you quit while a sound is ringing. Players never see it, and the program is ending anyway, so it's harmless. Stopping every sound on exit didn't remove it, because Godot's audio thread frees sounds a moment later. **Other ways:** wait a frame after stopping sounds before quitting (needs a custom quit path), or ignore it, as most Godot games do.

## 2026-11-04: Button clicks connected twice

**Problem:** while adding sound, every button gets its click sound automatically when it appears. Menus that rebuild their rows add the same button again, so the click was connected a second time and Godot reported errors. Found by the tests.

**Fix (code):** check `is_connected()` before connecting.
- Files: `scripts/autoload/audio.gd`

**Other ways:** give each menu its own click code (more repeated code), or use Godot's `CONNECT_REFERENCE_COUNTED` flag. Checking first is the simplest to read.

## 2026-11-04: New building data loaded half-broken

**Problem:** while making the shipping box movable, its building data came out as a plain `Resource` with none of its fields, and the Build tool crashed. Found by the tests, before you saw it.

**Fix (code):** `GameState` had `preload`ed the building list. The shipping box's own script uses `GameState`, so this was a loop: each needed the other to exist first. The list is now loaded with `load()` when the game starts.
- Files: `scripts/autoload/game_state.gd`

**Other ways:** store the scene's file path instead of the scene itself and load it only when placing, or have the box's script reach `GameState` without naming it at compile time. Loading at start was the smallest change.

## 2026-11-04: Hard grass squares around objects

**Problem:** after tilling a big field, the grass left under the stall, house, well and lanterns showed as hard green squares, because tiles meet in straight lines along the grid.

**Fix (code, plus an image made by a script):** a new `SoilEdges` node draws ragged bits of grass over the edge of any soil tile that touches grass, so the border wobbles like a real field. The bits are cut from the existing grass texture by `tools/build_curse_edges.gd`, the same trick already used for the curse border, so no new art was needed. Both now share one base script, `TileEdges`.
- Files: `scripts/farm/tile_edges.gd`, `soil_edges.gd`, `curse_edges.gd`, `assets/tiles/grass_edge.png`

**Other ways:**
- **Transition tiles (autotiling), the most common way.** An artist draws extra tiles for every edge and corner (a set of 16 or 47 pieces), and Godot's TileMap *terrains* pick the right piece from the neighbors. It looks the best when hand-drawn, but it needs that art, and AI images rarely line up well enough across 16 to 47 pieces.
- **A base sprite under each object:** a patch of dirt or stone under the stall. It only fixes objects, not every field edge.
- **Don't allow tilling right beside buildings,** leaving a path. A good idea for later for layout, but it doesn't fix the edges either.

## 2026-11-04: Tilled soil could never be removed

**Problem:** once ground was tilled it stayed soil forever, so after playing a while the whole shore was brown.

**Fix (code and one data number):**
- The Hoe on empty soil (no crop) turns it back into grass.
- Soil with no crop for 3 nights turns back into grass by itself. The number is `soil_idle_nights` in `data/balance.tres`, and each tile's night count is saved.
- Facing empty soil warns "Empty soil: grass returns tonight." on its last night, so the rule isn't a surprise.
- Files: `scripts/farm/farm.gd`, `game_balance.gd`

**Other ways:** most farming games do the same: unplanted soil slowly turns back to grass overnight, sometimes by random chance instead of a fixed count. A fixed count is easier to understand and to test. Some games also add a separate tool (a pickaxe or shovel) to clear soil, but reusing the Hoe keeps one less tool to learn.
